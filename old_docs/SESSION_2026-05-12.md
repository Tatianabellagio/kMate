# Session summary — v3 panel locked in (2026-05-09 → 2026-05-12)

This session resolved the "v3 cactus_em is 2× worse than v2" mystery and locked in v3 as the production panel. Below is the narrative arc, what was learned, and what's left.

## TL;DR

- **Bug found**: v3 simulation FASTAs (`imputed_fastas/`) were built from a Beagle-imputed VCF (`imputed_151.vcf.gz`), while cn_full_v3 was built from the unimputed `founders_231_chr.haploid.vcf.gz`. Reads from PG founders carried k-mers cn_full didn't know about → cactus_em's EM dumped that signal onto cactus founders.
- **Fixed**: all 231 founder FASTAs rebuilt from the unimputed VCF (`unimputed_fastas_v3/`). All cov10 sims regenerated.
- **Result**: v3 cactus_em now within 3-30% MAE of v2 baseline across all regimes (cov10 n200_g1 ★★ MAE 0.0096 → 0.0130).
- **Residual issue**: +41% cactus over-credit still present in h (was +90% before fix). Visible as ~0.02% of records — PG-specific variants in Chr1q knob region (Mb 21-23) — getting systematically underpredicted. Manageable.

## The investigation arc (chronological)

### Day 1 (2026-05-09) — hapFIRE constraints + first v3 panel diagnostics
- Established v3 panel cannot be directly consumed by hapFIRE/HARP (3 structural constraints: phased GTs, biallelic-per-pos, IUPAC-N ref). Built `chr1_only_panel_v3/` with carrier-status collapse + dedup as DIAGNOSTIC ONLY.
- Identified `parse_freqk_to_per_record.py` bug: groupby on `(chrom, pos, ref_len, alt_len)` collapsed distinct ALTs to mean=0.5 on v3's heavy multi-allelic atomization. Fixed by changing groupby to `(chrom, pos, ref, alt)`. freqk-v3 SNP R² jumped from 0.002 to ~0.7.

### Day 2 (2026-05-10) — Centromere + initial v3-vs-v2 gap analysis
- Verified v3 cactus_em-v3 has a real 2× MAE gap vs v2 on shared records with identical truth.
- Found centromere (Chr1 Mb 14-17) is a 10× local amplifier of the gap.
- Tried filtering missing genotypes and centromere — neither recovered v2 quality.

### Day 3 (2026-05-11) — The diagnostic that nailed the cn_full bug
- Pure-pool tests: PG founder 5151 in 100% pool gave h[5151]=0.65 (expected 1.0) with 0.25 mass leaked to cactus founders. Cactus founder 10002 in 100% pool gave h=0.986 ✓.
- The asymmetry was unambiguously on the PG-founder side.
- Tried cn_full singleton-k-mer filtering (filt2/filt3/filt5/filt10) — none recovered v2 quality.
- Diagnosed: PG simulation FASTAs were built from a Beagle-imputed VCF; cn_full_v3 was built from the unimputed VCF. Different variant sets → reads carried k-mers cn_full didn't know about.

### Day 4 (2026-05-12) — The fix
- Built `unimputed_fastas_v3/` for all 231 founders (`build_unimputed_v3_fastas.sh`, ~5min per founder, ran 231-task array).
- Replaced `founder_fastas_231/` symlinks (`setup_v3_consistent_fastas.sh`).
- Backed up old artifacts: `imputed_fastas_v2_DEPRECATED/`, `founder_fastas_231.v2_imputed_BACKUP/`, 4× `cov10_*_v2_imputed_BACKUP/` sim dirs.
- Rebuilt all 4 cov10 sims (n200_g1, n50_g1, n50_g3, n50_g3_skewed) from scratch.
- Re-ran all 5 method types on each (cactus_em global, cactus_em ★★, hapfire-v3, hapfire v2panel+v3proj, freqk-v3).
- Regenerated `FINAL_RESULTS_cov10_v3.ipynb` with v3-clean numbers.
- Archived `FINAL_RESULTS_cov10_v3_arms_only.ipynb` (centromere exclusion no longer materially changes conclusion).

## Decisions

1. **v3 panel locked in for production.**
2. **Default method: `cactus_em-v3 global`** — cleanest, near-v2 on all easy/medium regimes, and natively handles SVs.
3. **★★ window+smooth only for high-recomb scenarios** (e.g., n50_g3-style late-generation evolved pools).
4. **Real GrENE-Net data should be fine** — the residual cactus-vs-PG bias is a simulation observation; real samples are real plants, not consensus FASTAs.

## Residual issue (filed for future work)

The +41% cactus h-bias is **intrinsic to cn_full_v3** — cactus founders have richer k-mer fingerprints (private-assembly variants) than PG founders. The EM weighs k-mer evidence and cactus founders simply have more k-mers per pool fraction.

Most predictions are fine because the cactus-vs-PG carrier rates are similar for most variants → the h-bias cancels in projection. The 0.02% of records where the carrier rates differ extremely (PG-specific variants, mostly Chr1q knob Mb 21-23) get systematically underpredicted.

**Path forward**: develop a k-mer **rebalancing** strategy on the 231-founder panel (per-founder budget equalization / row-normalized cn_full / per-bubble per-founder k-mer cap) to remove the asymmetry directly. See `BALANCING_KMERS.md`. **Beagle imputation is NOT considered** — see `feedback_no_beagle_solutions.md` for why (hard-rejected for SVs, −25 to −30pp concordance loss).
