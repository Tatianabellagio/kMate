# Session 2026-05-17 — multi-allelic filter ordering bug + v3qc-v2 rebuild

This session uncovered a structural bug in our v3qc filter pipeline and rebuilds the panel with corrected decompose-first ordering. See `SESSION_2026-05-16.md` for the original v3qc design that this session corrects.

## TL;DR

- **Bug**: All record-level filters (`V4`, `PG-MAC<2`, `AC=0`) were applied to multi-allelic VCFs. `bcftools view -e 'INFO/X...'` on per-ALT vector INFO fields uses **OR-semantics by default** — drops the whole record if ANY ALT triggers the expression, including the legitimate ALTs.
- **Impact**: ~600K legitimate biallelic records silently destroyed across the genome. PG founders carrying real ALT k-mers at MIXED multi-allelic records had their carrier info wiped after merge → cn_full reconstructed them as REF → EM h vector collapsed to cactus (30× bias toward cactus side observed in SEEDMIX_S1 test).
- **Fix**: decompose multi-allelics into biallelic records BEFORE applying any record-level filter (`bcftools norm -f REF -m -any | bcftools sort`). With biallelic records, each filter expression evaluates per-ALT correctly.
- **Empirical confirmation**: of 48,679 MIXED multi-allelic records on Chr1 in old pangenie_153_qc, 0 survived the PG-MAC<2 filter (the OR-semantics bug killed all). The V4 filter dropped 114,067 MIXED records the same way.
- **Locked-in rebuild pipeline (v3qc-v2)** drops the PG-MAC step entirely (see below for the empirical reasoning).

## Why PG-MAC<2 is removed (not just deferred)

On the corrected per-ALT biallelic pangenie_153_qc_v2 (post-V4) on Chr1:

| AC pattern | Count | What it is |
|---|---:|---|
| AC = 0 | 810,576 | PG mono-REF — variant only in cactus side, PG founders all 0/0 |
| **AC = 1** | **0** | **V4 already removed all of these** |
| AC = 2 | 195,293 | Singleton hom-alt OR doubleton-het (V4 keeps the hom-alt ones) |
| AC = AN (306) | 1,517 | Real mono-ALT common variants |

**V4 mathematically forces AC=1 drops in diploid PG.** For AC=1 in diploid, the only GT pattern is exactly one founder = `0/1` (het); all others 0/0 or `./.`. This forces AC_Het = 1, giving V4 = 1/1 = 1.0 ≥ 0.01, dropped.

So **MAC<2 adds nothing beyond V4 + post-merge AC=0**:

| Step | What MAC<2 lower-end (AC<2) does that V4 + AC=0-cleanup doesn't |
|---|---|
| AC=0 records | post-merge AC=0 cleanup catches these — but ONLY if cactus also has no carriers. If cactus has carriers, post-merge keeps them (real cactus-only variants we want). PG-MAC would have dropped them prematurely → exactly the v3qc bias mechanism. |
| AC=1 records | V4 already drops all of these (proven empirically + mathematically) |

| Step | What MAC<2 upper-end (AN-AC<2) does — pure harm |
|---|---|
| AC=AN mono-ALT records | 1,517 real common variants on Chr1, dropped for no biological reason |
| AC=AN-1 near-mono-ALT | also real common variants |

**MAC<2 adds zero useful filtering after V4 — it just adds premature cactus-only variant drops + harmful upper-end drops.**

## Locked v3qc-v2 pipeline

1. **GQ ≥ 20** cell mask on per-sample PanGenie VCFs (reused from v3qc — already done)
2. Merge per-sample PG → pangenie_153_raw (reused)
3. **`bcftools norm -f REF -m -any | bcftools sort`** on cactus_78 AND pangenie_153_raw → biallelic (NEW)
4. **`bcftools +fill-tags`** AC, AN, AC_Het, F_MISSING on biallelic PG (NEW order)
5. **V4 < 0.01** filter on biallelic PG (now per-ALT correct)
6. **NO PG-MAC step** — V4 already catches singleton-hets; post-merge AC=0 handles ghosts
7. Merge cactus_78_bi + pangenie_153_qc_v2
8. **`bcftools norm -m -any` again** (catches multi-allelics re-created by merge)
9. fill-tags + AC=0 cleanup
10. Build cn_full, cn_var, FASTAs from corrected VCF

## Decision: PanGenie-index rebuild parked (use pang_135 as canonical)

**2026-05-17.** Attempted to rebuild PanGenie-index from the v3qc-v2 VCF for paper-quality methodological self-consistency (job 62889). Result: **failed at Step 3** — PanGenie-index requires a clean pangenome graph structure with non-overlapping bubbles. Our v3qc-v2, derived from cactus_78 + pangenie_153_qc_v2 via merge, has some overlapping indel records that break the graph invariant. Error: `variant at Chr1:879 overlaps previous one. VCF does not represent a pangenome graph.`

**Decision: don't rebuild. Use pang_135 (the original minigraph-cactus pangenome PanGenie-index) as the canonical k-mer dictionary.**

Justification:
- PanGenie's design intends `PanGenie-index` to be run **once on the source pangenome graph**, not rebuilt per analysis. Per-sample genotyping then runs against this fixed index. Our pipeline (cn_full + EM on top) uses the index correctly per PanGenie's intended workflow.
- The pang_135 index represents the full structural diversity captured by 135 long-read assemblies — more variants than our 80-cactus subset alone. Using it preserves k-mer evidence for variants in the broader pangenome context.
- The "var-dedup over-aggression" concern (k-mers dedup'd in 135-asm context that are now informative in our 231-founder panel) is a small inefficiency, not a bias source. v3 baseline (which uses pang_135) achieves balanced h.

Future revisit options if maximum k-mer coverage is needed:
- (a) Apply `vcfbub -l 0 -r 100000` to v3qc-v2 to flatten overlapping bubbles before PanGenie-index → ~1 h additional SLURM
- (b) Write a custom per-allele k-mer extractor that doesn't require pangenome graph structure (~1-2 day dev)
- (c) Accept the trade-off and cite pang_135 as the canonical k-mer source in paper methods

Paper-defensible methods statement:
> "The pangenome graph from 135 long-read A. thaliana assemblies (vcfbub-flattened, processed via minigraph-cactus) provides the k-mer dictionary via PanGenie-index. Our 231-founder analysis panel is a subset of variants from this graph after QC filtering, with founder genotypes from cactus assembly paths (80 founders) or per-sample PanGenie genotyping of 1001G short reads (151 founders, of which 2 substitute for low-quality cactus assemblies). cn_full carriers are determined by intersecting each founder's reconstructed haplotype (from v3qc-v2 GTs, treating missing genotypes as ambiguous via the --treat-missing-as-n flag in build_kmer_cn.py) with the bubble-level k-mer dictionary from PanGenie-index."
