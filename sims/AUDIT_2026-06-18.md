# Sim-framework audit — 2026-06-18

Audit of the pool-seq simulation framework (`sims/scripts/make_recomb_mosaics.py`,
`sims/scripts/compute_recomb_truth.py`, and the `benchmarks/{p80,p231}/scripts/06*`
drivers), triggered by discovery of a Chr2-contamination bug while adding the
97%-selfing regime. Three real bugs + two minor items.

## 🔴 Bug #1 — Chr2 sequence leaking into mosaic Chr1 tails  (FIXED)
`fa_fetch()` did not clamp the fetch end to the sequence's real length. Founder
**consensus** Chr1 is shorter than TAIR10 for **81% of the 231 founders**
(median −204 kb, max −431 kb; net consensus deletions). Fetching the TAIR10
window `[1, 30427671]` therefore ran off the end of Chr1 into the next record,
splicing the literal `>Chr2` header + the first ~0.7–1.4% of Chr2 into the
distal tail of every mosaic "Chr1". Because the stray `>` lands mid-line after
80-col wrapping, `samtools faidx` absorbed it silently as garbage "bases".

- **Affected:** the distal ~0.7–1.4% of Chr1 in *every* mosaic, in *every*
  existing regime (g0 included — pure founders overrun the most).
- **Effect:** reads only. Truth is computed by projecting `var_pa` and never
  reads the FASTA, so at tail records truth = founderX's allele while the reads
  are Chr2 → inflated estimator error confined to the Chr1 tip.
- **Fix:** clamp `e = min(end, length)` and **N-pad** the deficit so every
  mosaic Chr1 stays exactly the requested TAIR10 length (region.bed / VISOR /
  truth coords stay aligned). N tail ⇒ VISOR emits no reads there (honest
  "no data") instead of actively-wrong Chr2 reads.

## 🔴 Bug #2 — `compute_recomb_truth.py` stale after the cn_var→var_pa rename  (FIXED)
The 2026-05-29 `cn_var→var_pa` rename updated the drivers + data but not this
script. Its argparse still defined `--cn-var/--cn-var-meta`, while all three
drivers call it with `--var-pa/--var-meta` ⇒ **argparse crash; the pipeline
could not re-run.** Worse, the called-mask auto-detect did
`path.replace(".cn_var.npz", ".cn_var_called.npz")`, which silently no-ops on a
`.var_pa.npz` name and would have loaded the **carrier matrix as the called
mask** (denom = carriers, not called) ⇒ silent wrong-MAR truth. Existing truth
files predate the rename, which is why they exist and look correct.

- **Fix:** CLI is now `--var-pa/--var-meta` (with `--cn-var/--cn-var-meta` kept
  as legacy aliases) + an explicit optional `--var-called`. The derivation now
  handles `.var_pa.npz`→`.var_called.npz` and errors loudly rather than ever
  loading the carrier matrix as the called mask.

## 🟠 Issue #3 — coordinate drift understated in the methods doc  (DOCUMENTED, not fixed)
`docs/SIMULATIONS_METHODS.md` §3.1 claimed consensus FASTAs are "near-identical
length" and slicing is "exact and trivial (±few bp)." Real drift is up to
**200–430 kb**. For **pure founders** (all of g0, ~94% of g3 individuals under
97% selfing) this is harmless — kMate is k-mer-based / position-independent. For
**recombinants** it mis-registers TAIR10-coord breakpoints against drifted
consensus by the cumulative-indel offset; in **global mode** (production /
benchmark) the net effect on the chromosome-wide mixture is small and averages
over the pool. A correct fix needs consensus→TAIR10 alignment per breakpoint —
the same machinery the doc explicitly scopes out for raw assemblies — so it is
left as a documented limitation, not fixed here.

## 🟡 Minor
- `make_one_mosaic()` was dead code (no callers) → **deleted**.
- Gen-0 founders are drawn twice (once in `main()` for `pool_weights.tsv`, again
  in `make_individuals()`). Harmless: truth follows `ancestry.tsv`, and all
  production runs use `--gen0-no-replace` where the founder *set* is identical.
  `pool_weights.tsv` can disagree with the realized draw only on the unused
  legacy (with-replacement) path. Left as-is; flagged.
